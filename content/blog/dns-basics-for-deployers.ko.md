배포는 했고 주소가 못생겼어요. `myapp.sitey.my`를 붙이고 싶은데 그 사이에 DNS가 있습니다. 필요한 개념은 넷이에요.

## 이름은 질문이고, 답에는 종류가 있다

브라우저가 `myapp.sitey.my`를 열면 DNS에 「이게 뭐야?」라고 묻고, 답이 **레코드**예요. 레코드에는 종류가 있고 셋만 알면 됩니다.

**A 레코드 — 「이 IP 주소다」**
서버에 고정 IPv4가 있을 때(VPS·클라우드 VM). sitey는 IPv4만 받아요.

**CNAME 레코드 — 「저 다른 이름과 같다」**
Vercel·Netlify·GitHub Pages처럼 호스팅이 IP 대신 호스트명을 줄 때. 규칙 둘: 자기 자신을 가리킬 수 없고, **상대 호스팅이 내 이름을 알아야** 해요. CNAME은 연결을 넘길 뿐 소개를 해주지 않아서, 호스팅 설정에 `myapp.sitey.my`를 넣지 않으면 404나 인증서 오류가 납니다. 「DNS가 깨졌다」는 신고의 대부분이 이 경우예요.

**TXT 레코드 — 「이 문자열을 보여준다」**
호스팅이 소유 확인용 토큰을 주면 여기에 올려요. Vercel은 루트(`_vercel.sitey.my`)에서 찾기 때문에 sitey도 거기에 씁니다. 여러 사람 값이 한 이름에 나란히 있고, 내 값은 덧붙여지지 덮어쓰지 않아요.

## TTL — 답을 얼마나 오래 기억해도 되나

레코드마다 초 단위 수명이 있고, 리졸버는 그동안 다시 묻지 않고 답을 재사용해요. 그래서 DNS가 빠르고, 그래서 변경이 즉시 안 보입니다.

- 새 이름은 금방 보여요
- 바뀐 이름은 옛 답을 든 리졸버가 만료될 때까지(보통 몇 분) 늦을 수 있어요
- 남의 캐시는 못 비워요. 원본이 맞는지 확인하고 기다리는 것뿐

## 전파 — 사실 전파는 없다

레코드가 인터넷으로 서서히 퍼지는 게 아니에요. 레코드는 sitey 네임서버 한 곳에 있고 API가 응답한 순간 거기서는 이미 맞아요. 나머지는 각자의 캐시가 제 속도로 만료되는 것뿐입니다.

```bash
dig +short @ns1.sitey.my myapp.sitey.my   # 원본. 즉시 맞거나, 레코드가 틀린 것
dig +short @1.1.1.1 myapp.sitey.my        # 공용 리졸버. 캐시가 돌면 맞음
dig +short myapp.sitey.my                 # 내 리졸버 + OS 캐시
```

첫 줄이 맞고 나머지가 틀리면 기다리세요. 첫 줄이 틀리거나 비어 있으면 기다려도 소용없어요.

## 「열린다」와 「이름이 풀린다」는 다르다

이름이 풀린다는 건 답이 있다는 뜻이고, 열린다는 건 그 답에서 무언가 페이지를 준다는 뜻이에요. sitey는 만들 때 `reachable`로 그 차이를 알려줘요. `false`는 「이름은 있고 아직 아무것도 안 뜬다」이고, 배포 전에 이름을 먼저 잡을 때 당연한 상태예요.

## 한 번의 호출

```bash
curl -X POST https://sitey.my/api/v1/subdomains \
  -H 'content-type: application/json' \
  -d '{"subdomain":"myapp","domain":"sitey.my","type":"A","value":"203.0.113.10"}'
```

응답의 `owner_token`을 저장하세요. 한 번만 보여주고, 레코드를 고칠 유일한 열쇠예요. 나머지 API는 [/openapi.json](/openapi.json), 에이전트용 요약은 [/llms.txt](/llms.txt).

## 용어

- **존:** 한 도메인 아래 모든 레코드를 담은 파일. 내 서브도메인은 그 안의 한 줄
- **네임서버:** 존에 대해 답하는 서버. sitey는 `ns1.sitey.my`·`ns2.sitey.my`를 직접 운영해요
- **리졸버:** 내 컴퓨터가 묻는 서버. 대신 물어보고 캐시해요
- **루트(apex):** 앞에 아무것도 없는 `sitey.my`. 발급 대상이 아니에요
- **라벨:** 점으로 나뉜 조각 하나. 서브도메인은 라벨 하나라 점이 들어갈 수 없어요
